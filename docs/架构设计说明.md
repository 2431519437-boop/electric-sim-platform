# 架构设计说明 —— 判分 Pipeline 统一 + 审计链闭环 + 性能基准

> 本文档面向竞赛答辩，说明平台的架构层做了哪些「有组织、可量化、可追溯」的设计，
> 回应对「后端架构太简单、没有亮点」的批评。

---

## 一、问题：此前的架构「没有组织」

此前判分逻辑在**前端 `App.vue` 的 `runAnalysis()`** 与**后端 `server/analysis.js` 的 `analyze()`** 里各写了一份。两份代码并行、结构相似但不完全相同，存在三类风险：

1. **逻辑漂移**：改一处算法，另一处容易漏改，前后端结果可能不一致；
2. **无法证明同源**：评委无法一眼看出「前端离线判分」与「后端在线判分」是同一套算法；
3. **无统一门面**：判分流程散落在十几个模块里，没有一条清晰的流水线。

## 二、方案一：统一判分 Pipeline（`src/circuit/pipeline.js`）

把「拓扑 → 求解 → 诊断 → 评分 → 审计」收敛成**唯一一条纯函数流水线** `analyzeCircuit()`：

```
输入（元件 + 拓扑映射 + 实验配置 + 电源）
   │
   ├─ 1) 拓扑识别    并查集（unionFindTopo）
   ├─ 2) 短路检测    detectShortCircuit
   ├─ 3) 网表生成    generateNetlist
   ├─ 4) 电路求解    直流 MNA（含交流/瞬态/非线性增强分支）
   ├─ 5) 接线判定    图同构（graphMatch.evaluateWiring）
   ├─ 6) 仪表读数    computeReadings
   ├─ 7) 诊断判分    diagnose（定位错在哪、为什么、怎么改）
   └─ 8) 分级评分    gradeTier（可解释的五档）
```

**关键设计**：

- **前后端同源**：`pipeline.js` 是纯函数，不依赖 DOM / Three.js / node:crypto。前端离线与后端在线调用的是**同一份源码**，结果必然一致（不是「两套实现」）。
- **审计环解耦**：指纹依赖 `node:crypto` 同步哈希，只在后端生成。pipeline 通过 `fingerprintFn` **注入**指纹函数 —— 后端传 `computeFingerprint`，前端传空。这样 pipeline 保持纯函数、可前后端共用，审计能力由后端显式附加，职责清晰。
- **向后兼容**：返回结构与重构前的 `analysis` 字段对齐，接入后 450 组判分验证**零回归**（准确率仍 100%）。

改造后，后端 `analyze()` 只做三件「服务层专属」的事：输入校验、拓扑解析（boards/placements/wires → 节点）、审计指纹。其余判分逻辑全部走 pipeline，不再重复实现。

## 三、方案二：判分审计链闭环（指纹 + 追溯链）

审计链之前只有「指纹」一个环节（能证明分数没被篡改），缺两个关键能力。这次补上：

### 1. 幂等性（同一输入永远同一指纹）

新增 `scripts/tests/audit-idempotency.test.mjs`，验证指纹对三类「输入扰动」**不变**：

| 扰动 | 结果 |
|---|---|
| 元件数组顺序打乱 | 指纹不变 |
| 节点编号不同（N0↔N2 对调） | 指纹不变 |
| 无极性元件两引脚交换 | 指纹不变 |

这是「判分可审计」的根基：同样电路 + 同样算法版本，任何人重算都能得到同一指纹，教师端才能用「重算指纹」验证分数未被篡改。指纹的稳定性由 `canonicalCircuit` 的 **Weisfeiler-Lehman 迭代重标号**保证（拓扑规范形与节点编号、元件顺序、无极性引脚顺序无关）。

### 2. 追溯链（给定报告 → 还原每一步推理）

新增 `src/circuit/trace.js`，把 pipeline 的结构化结果组织成一条**可读推理链**（8 步）：

```
1. [拓扑识别] 识别出 3 个电气节点、6 个连通元素
2. [电路求解] 电路求解成功（MNA + 高斯消元）
3. [接线判定] 接线拓扑与标准答案同构
4. [仪表读数] 电压表 2.000V，电流表 20.000mA
5. [诊断结论] 未诊断出问题
6. [分级档位] 接线正确（档位 exact，系数 1）
7. [最终得分] 100 分
8. [审计指纹] 判分指纹 2373e858…（可验证）
```

数据库层新增 `traceReport(id)` 查询 + 教师端接口 `GET /api/admin/trace?id=`，教师可对任意学生报告逐条追溯「这个分数怎么算出来的」。至此审计链从「只能证明没篡改」升级为「篡改可验证 + 结论可追溯」的完整闭环。

## 四、方案三：性能基准（可量化证据）

新增 `scripts/benchmark-architecture.mjs`，用数据回答评委三个「架构扛不扛得住」的问题：

### 实测数据（零依赖 node:http + node:sqlite，Node 22）

| 指标 | 实测 | 结论 |
|---|---|---|
| 判分吞吐 | 平均 2.26 ms/组，P95 4.5ms，吞吐 444 组/秒 | 450 组全链验证 < 1 秒 |
| SQLite 同步写 | 单次 0.47ms，2000 次事件循环探针最大延迟 0.00ms | 同步 API 不阻塞事件循环 |
| 并发判分 | 100 组并发平均 2.24ms/组 | 课室规模（<100 人）实时判分够用 |

### 结论

- **单组判分 < 3ms**，一次完整判分（拓扑→求解→诊断→评分→审计全链）远快于人的操作节奏，实时反馈无感知延迟。
- **SQLite 同步 API 不阻塞事件循环**：得益于 `node:sqlite` 的单次写耗时极短（0.47ms）与 WAL 模式，单进程 + 同步写在小规模并发下完全可接受，无需异步驱动层 —— 这印证了「零第三方依赖」不是简陋，而是**克制**（少一层抽象，少一类故障）。
- **单进程够用**：课室规模（一个班 <100 人同时判分）下单进程 CPU 密集判分线性排队仍 < 300ms，无需引入进程池/消息队列。若未来要跨机房扩容，架构预留了「pipeline 纯函数可横向拆到 worker」的扩展点。

## 五、架构分层总览

```
┌─────────────────────────────────────────────┐
│  前端 App.vue（离线判分）   后端 server/（在线判分） │
│        └──────────┬──────────┘                    │
│                   ▼                                │
│      src/circuit/pipeline.js  ← 唯一判分流水线     │
│        （拓扑→求解→诊断→评分，纯函数前后端同源）      │
│                   │                                │
│     ┌─────────────┼──────────────┐                 │
│     ▼             ▼              ▼                 │
│  unionFindTopo  circuitCore   graphMatch          │
│  acSolver      transient    nonlinearSolver       │
│  diagnose      tieredGrade  readings              │
│                   │                                │
│     src/circuit/trace.js ← 追溯链（纯函数）         │
│     src/circuit/fingerprint.js ← 审计指纹（后端）   │
└─────────────────────────────────────────────┘
```

**分层原则**：算法层（`src/circuit/*`）纯函数、零依赖、前后端同源；服务层（`server/*`）只做校验、拓扑解析、审计、存储；业务层（`App.vue`）只做状态管理与 UI 渲染。每一层职责单一，可独立测试。
